# TASK 6 — Autonomous Execution & Safety

## Completed
The execution lifecycle: create an execution for a policy-allowed move, approve it
(explicit guardrail), submit through the KeeperHub client, track the full state
machine, and expose user-scoped list/get. Safety is enforced server-side at every
step.

## API
| Endpoint | Behavior |
|---|---|
| `POST /api/executions` | Creates a `PENDING` execution for `{wallet_id, asset, source_protocol, target_protocol}` after **re-verifying policy server-side** |
| `GET /api/executions` | Lists the caller's executions (newest first) |
| `GET /api/executions/{id}` | One execution (404 for other users) |
| `POST /api/executions/{id}/approve` | Owner approval → submit via KeeperHub → `SUBMITTED` → (polled) `COMPLETED`/`FAILED` |
| `POST /api/executions/{id}/reject` | `PENDING` → `REJECTED` |
| `POST /api/executions/{id}/cancel` | `PENDING`/`APPROVED` → `CANCELLED` |
| `POST /api/executions/{id}/refresh` | Poll the execution layer for a `SUBMITTED` execution's latest status |

## Safety model (each backed by a test)
1. **Policy re-verification at execution time** — the client only points at a
   wallet/position/target; the service re-fetches the position, looks up the target
   opportunity, and re-runs `evaluate_opportunity` with the user's *current*
   preferences. Blocked moves → 400 with the policy reasons.
2. **Same-protocol guard** — moving to the position's current protocol is rejected.
3. **Unknown target guard** — a target not in the market returns 404.
4. **No concurrent executions on a position** — one in-flight execution
   (pending/approved/submitted) per wallet+asset blocks creation with 409.
5. **Explicit approval** — nothing reaches the execution layer until the owner
   approves. (An autonomous "auto-approve" sweep is a future flag, kept off by default.)
6. **Strict state machine** — transitions are validated: approve only `PENDING`,
   reject only `PENDING`, cancel only `PENDING`/`APPROVED`, refresh only `SUBMITTED`.
7. **Full isolation** — every operation is user-scoped; cross-user fetch/action → 404.

## Lifecycle
`PENDING → APPROVED → SUBMITTED → COMPLETED | FAILED`
(with `REJECTED`/`CANCELLED` off `PENDING`, `CANCELLED` off `APPROVED`).

The mock client returns an immediate `completed` receipt (with a deterministic tx
hash), so the full chain is visible in one call; the `SUBMITTED → poll → terminal`
path is covered by a test using a stubbed client.

## Security
- **Server-side policy gate**: execution creation re-runs the policy engine with fresh
  position + preferences data; a client cannot execute a move its own UI blocked.
- **Guardrails before any state change**: duplicate in-flight checks and strict state
  transitions are enforced in the service, not the route layer — no path bypasses them.
- **User scoping**: `_load_execution` requires `user_id` match (404 otherwise);
  wallet/position lookups join through the owner. No cross-user access possible.
- **Audit integrity**: every lifecycle step writes an `AuditLog` row linked by
  `execution_id`, producing a complete, inspectable trail (execution.created →
  … → completed/failed/rejected/cancelled).
- **No secrets**: tx hashes and amounts only; no private keys or signatures pass
  through this layer (KeeperHub holds wallet custody).

## Architecture
- `ExecutionAction`/`ExecutionReceipt` keep the service decoupled from KeeperHub's
  transport; swapping mock→real touches one factory.
- Lifecycle transitions are simple `if` guards on the enum — easy to audit; a future
  state machine library is unnecessary at this size.
- The service accepts an injectable client for tests (no monkeypatching), and the
  route layer maps domain errors → HTTP codes consistently (400/404/409).

## Dependencies
- No new dependencies.

## Configuration
- No new knobs; client selection reuses `KEEPERHUB_MOCK`.

## Recommendations (non-blocking)
